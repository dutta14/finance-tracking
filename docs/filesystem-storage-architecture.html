Architecture Plan: Filesystem-Based Storage

Replace localStorage/IndexedDB with File System Access API — app becomes a viewer for a data folder.

Overview

The app reads and writes data to a user-selected folder on the local filesystem. The folder can live anywhere — including a Google Drive–synced directory — making the app a pure view of data that can be shared by copying the folder.

Key principle: Data lives in the shared folder (filesystem). Settings stay in localStorage (device-local). Two people sharing the same folder see identical data but can have different themes/layouts.

Technology: File System Access API

Browser-native API (Chrome/Edge). User picks a folder once → app gets read/write access. Handle is persisted in IndexedDB so the user doesn't re-pick every session.

FileStore API

// src/utils/fileStore.ts

interface FileStore {
  init(handle: FileSystemDirectoryHandle): Promise<void>
  readJSON<T>(path: string): Promise<T>
  writeJSON(path: string, data: unknown): Promise<void>
  readCSV(path: string): Promise<string[][]>
  writeCSV(path: string, rows: string[][]): Promise<void>
  readBinary(path: string): Promise<ArrayBuffer>
  writeBinary(path: string, data: ArrayBuffer): Promise<void>
  exists(path: string): Promise<boolean>
  listFiles(dir: string): Promise<string[]>
  delete(path: string): Promise<void>
  getHandle(): FileSystemDirectoryHandle | null
  subscribe(path: string, cb: () => void): () => void
}

Design decisions

  • All reads/writes are async
  • In-memory cache for hot data (accounts, current year balances)
  • Writes are debounced (300ms) to batch rapid edits
  • Folder handle persisted in IndexedDB for session continuity
  • Uses navigator.locks to prevent concurrent writes from multiple tabs
  • Uses BroadcastChannel for cross-tab cache invalidation — when any tab writes, it broadcasts { path, timestamp }; other tabs invalidate their cache for that path and re-read from disk
  • MemoryFileStore — same interface backed by a Map, used for demo mode and all unit tests

Execution Steps

Step 0 — Async migration audit

What: Classify every appStorage.getJSON / localStorage.getItem call site to understand the sync→async blast radius before changing anything.

Why: Today appStorage.getJSON() is synchronous (reads from an in-memory Map). fileStore.readJSON() returns a Promise. Every call site that reads in a render path (not in a useEffect or event handler) needs a state + loading pattern. This audit prevents surprises during steps 3–6.

Process:

  1. Grep all appStorage.getJSON and localStorage.getItem calls (~300 across ~48 files)
  2. Classify each as: (a) already in effect/handler — trivial to make async, (b) in render/initializer — needs state + effect refactor, (c) in a synchronous utility function called from render — needs the utility to become async or the caller to pre-load
  3. Document the list of category (b) and (c) call sites — these are the migration's real work items

Known category (b)/(c) hotspots:

  • budgetStorage.ts → getBudgetSaveRate() — called synchronously from GoalDetailedCard render path
  • searchIndex.ts — builds search index synchronously from appStorage reads
  • DataContext.tsx — initializes state via useState(loadAccounts) (synchronous initializer)
  • LeverageGoal.tsx — reads 5 localStorage keys inline during state initialization
  • PayDown.tsx — reads paydown-loans in state initializer
  • FICalculator.tsx — reads fi-simulations and user-profile in render path
  • demoMode.ts — reads/writes all keys synchronously

Output: A categorized spreadsheet (or table in this doc) of all call sites with their migration strategy.

Step 1 — Create fileStore.ts + MemoryFileStore + CSV utilities

What: Build the low-level filesystem abstraction that all other code will use, plus an in-memory variant for tests and demo mode.

Files created:

  • src/utils/fileStore.ts — Implements the FileStore interface (readJSON, writeJSON, readCSV, writeCSV, readBinary, writeBinary, exists, listFiles, delete, getHandle, subscribe). Includes BroadcastChannel integration: on every write, broadcasts { path, timestamp }; listens for broadcasts from other tabs and invalidates the in-memory cache for that path + fires local subscribers.
  • src/utils/memoryFileStore.ts — Same FileStore interface backed by a Map<string, string | ArrayBuffer>. No disk I/O, no permissions, no IndexedDB. Used for: (a) all unit tests — drop-in mock, (b) demo mode — seed fake data without touching real files.
  • src/utils/csvUtils.ts — parse CSV string → string[][], serialize string[][] → CSV string (handles quoting, commas in values, newlines)

Details:

  • Path resolution: takes relative paths like "balances/2024.csv", splits on /, navigates subdirectories via getDirectoryHandle(), reaches file via getFileHandle()
  • Auto-creates directories on write (recursive getDirectoryHandle(name, { create: true }))
  • Write debouncing: 300ms debounce per path — rapid edits batch into one disk write
  • In-memory cache: Map<path, data> populated on read, invalidated on write. Reads hit cache first.
  • Write locking: uses navigator.locks.request('filestore-write-' + path) to prevent concurrent writes from multiple tabs
  • Cross-tab sync: BroadcastChannel('filestore-sync') — on write, broadcast path; on receive, evict cache + notify subscribers
  • Error handling: wraps all FS operations in try/catch, distinguishes NotFoundError (returns null/empty) from NotAllowedError (bubbles up for re-permission prompt)

Tests: Unit tests using MemoryFileStore — no FS API mocking needed.

Step 2 — Create FileStoreContext + FolderPicker component

What: React context that initializes the file store and gates the app behind folder selection.

Files created:

  • src/contexts/FileStoreContext.tsx — Provider + useFileStore() hook
  • src/components/FolderPicker.tsx — UI for selecting/changing the data folder
  • src/utils/handlePersistence.ts — Save/restore FileSystemDirectoryHandle to IndexedDB (survives page refresh)

Details:

  • On app mount: try to restore handle from IndexedDB → call handle.requestPermission({ mode: 'readwrite' })
  • If no stored handle or permission denied → render FolderPicker instead of the app
  • FolderPicker calls window.showDirectoryPicker(), validates the folder (checks for accounts.json OR offers to create empty structure), persists handle to IndexedDB

  • disconnect() clears IndexedDB handle + in-memory cache → returns to FolderPicker

UX: Simple full-page screen: icon, "Select your data folder", description of what it expects, a single button.

Step 6b — One-time decrypt migration

What: Before deleting crypto.ts and encryptedStorage.ts, decrypt any remaining encrypted data in localStorage/IndexedDB and write it as plaintext to the filesystem.

Why: If this step is skipped and Step 7 deletes the crypto module, any data still stored in encrypted form becomes permanently unreadable.

Process:

  1. Check if encryption was enabled (localStorage.getItem('encryption-enabled') === '1')
  2. If yes, prompt user for their password → derive CryptoKey
  3. For each SENSITIVE_KEY in encryptedStorage.ts: read encrypted value from localStorage → decrypt → write plaintext to the corresponding filesystem path (per the migration map)
  4. For IndexedDB tax file blobs: read each blob → decrypt if encrypted → write as taxes/{year}/files/{filename}.pdf via fileStore.writeBinary()
  5. Verify: for each migrated key, confirm the filesystem file is readable and matches expected schema
  6. Set a migration-complete flag (localStorage.setItem('fs-migration-complete', '1'))

Edge cases:

  • User forgot password → cannot decrypt → show "Your encrypted data cannot be migrated without your password" message. Allow proceeding with empty data (fresh start).
  • Encryption was never enabled → skip this step entirely, data is already plaintext in localStorage
  • Partial migration (user closes browser mid-step) → on next load, check flag, re-run for any missing files

This step must complete successfully before Step 7 deletes any crypto code.

Pros & Cons

Pros

  • Portable — copy folder = copy all data
  • No sync code — filesystem handles sync
  • Inspectable — human-readable JSON/CSV
  • No size limits — no 5-10MB localStorage cap
  • Shareable — shared folder = shared data
  • Backup-friendly — git, Time Machine, Drive version history
  • Simpler codebase — delete encryption, sync, migration code

Cons

  • Chromium-only — no Firefox/Safari
  • Permission UX — folder picker on first visit
  • Async refactor — all data reads become async
  • No encryption at rest — folder access = data access
  • Network drive offline — reads fail if folder unavailable
  • Multi-device conflict — last-write-wins without resolution

Export & Import (Post-Migration)

Export: The folder is the export. Zip it, copy it, put it on a USB stick.

Import: Point the app at a different folder. Done.

Share: Give someone the folder (via Drive, AirDrop, etc.). They open the app and point to it.

No code needed for any of these operations.
